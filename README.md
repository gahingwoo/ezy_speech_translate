# Project Documentation

## 1. Overview

EzySpeechTranslate is a two-server web system for live speech transcription and multilingual translation during events.

It solves a practical gap: one operator can speak and correct text in real time, while many viewers follow in their own language with optional text-to-speech playback.

Core features implemented in code:
- Live admin speech capture in browser (Web Speech API)
- Real-time interim and final transcript broadcast over Socket.IO
- Admin correction, deletion, import, clear, and export workflows
- Viewer-side translation mode and transcription-only mode
- A projection screen for the front of the room, on its own route
- Multiple rooms, each with its own feed, listeners and transcript
- Scripture recognition: references that were cited, and verses that were
  quoted without being named, looked up in a Bible rather than translated
- Server-side translation API with caching and retry logic
- Read aloud in the voices the reader's own device has
- Optional SQLite persistence, so a restart does not lose a service
- Interface in 22 languages, following whichever one the reader chose
- Session-based and token-based protections, rate limiting, input sanitization, and security logging
- Optional OEM branding from config

Tech stack (from runtime code and dependencies):
- Python 3.8+
- Flask 3, Flask-SocketIO 5, eventlet
- Flask-CORS, Flask-Limiter, Flask-Talisman
- PyJWT
- PyYAML
- requests
- Frontend: PatternFly 6 (vendored subset) + vanilla JavaScript, no build step
- Templates are generated by `tools/patternfly/render_*.py`; the files in
  `app/templates/` are outputs and are not edited by hand
- Real-time transport: Socket.IO (WebSocket + polling fallback)
- Translation provider: Google Translate web endpoint (`translate.googleapis.com`)
- Speech recognition: browser Web Speech API (admin client)
- Installs natively (systemd, its own account) or in Docker, updates from GitHub releases with automatic rollback, and has a Cockpit module

## 2. System Architecture

### High-Level Structure

- `app/user/server.py`
  - Primary backend and viewer UI host (default port `1915`)
  - Maintains translation history in memory
  - Exposes translation/export/history APIs
  - Handles Socket.IO events for viewers and admin-originated transcript actions

- `app/admin/server.py`
  - Admin/login frontend host (default port `1916`)
  - Handles admin session login and admin-facing API endpoints
  - Proxies room and glossary actions to user server

- `app/static/js/admin.js`
  - Admin workflow client: microphone capture, interim/final transcript emit, correction, reorder, import/export, health polling

- `app/static/js/user.js`
  - Viewer workflow client: live stream rendering, translation requests, TTS queueing, display/search/export settings

- `app/static/js/projection.js`
  - The screen at the front of the room: one room's feed, one language, three
    lines, no scrolling. Configured by query string or by its own wizard.
    See `docs/README_PROJECTION.md`

- `app/static/js/{theme,sidebar,wizard,typewriter}.js`
  - The parts more than one page needs: applying a theme, opening a sidebar,
    stepping through a wizard, typing text as it arrives

- `app/user/bible_detector.py`, `app/user/scripture_matcher.py`
  - Scripture that was cited by reference, and scripture that was quoted by
    wording. See section 5.2

- `app/db.py`
  - Optional SQLite persistence: transcripts, corrections, rooms, glossary

- `app/translation_service.py`
  - Server-side translation service wrapper with cache and retry/backoff

- `secure_loader.py` + `setup.py`
  - Loads and injects secrets from `config/secrets.key` (Fernet-encrypted)
  - Generates initial secrets and optional self-signed SSL certs

- `config/config.yaml`
  - Runtime configuration for ports, HTTPS flags, security limits, CORS, features, OEM branding

### Data/control flow

1. Admin logs in on admin server (`/api/login`) and gets JWT + session cookie.
2. Admin UI connects to user server Socket.IO and emits `admin_connect` with JWT.
3. Admin browser speech recognition produces interim/final transcript payloads.
4. User server validates and broadcasts:
   - interim: `realtime_transcription` (not persisted)
   - final: `new_translation` (persisted in in-memory history)
5. Viewer UI receives events, loads paginated history via `/api/translations` using per-socket API token from `ready` event.
6. Viewer UI requests translation via `/api/translate`; reading aloud is done by the browser.
7. Admin corrections and deletions are broadcast to all connected clients.

### Component communication

- Admin server ↔ User server: HTTP calls for rooms and glossary (localhost)
- Admin browser ↔ Admin server: login/session APIs
- Admin browser ↔ User server: Socket.IO for transcript operations and sync
- Viewer browser ↔ User server: Socket.IO + HTTP APIs

### Text diagram

```text
[Admin Browser]
  ├─ HTTP/HTTPS -> [Admin Server :1916]  (login/session, config)
  └─ WS/HTTP -> [User Server :1915] (admin_connect, new_transcription, corrections)

[Viewer Browser]
  └─ WS/HTTP/HTTPS -> [User Server :1915] (ready/api_token, history, translate, exports)

[Projection Screen]
  └─ WS -> [User Server :1915] (one room, one language, read-only)

[User Server]
  ├─ In-memory history + session token maps, written through to SQLite
  ├─ Google Translate endpoint (server first, browser as fallback)
  └─ Bible lookup + local wording index
```

## 3. User Perspective (User)

### 3.1 Non-native speakers

- Viewer flow is short: open URL, choose a reading language, read live lines.
- The browser's own language is detected and used until someone chooses.
- **One reading language, not two.** It is both the language the sermon is
  translated into and the language of the buttons and headings; there is a
  "Keep the page in English" switch for anyone who wants the old split.
- The interface is translated into 22 languages, including the strings the
  script writes rather than only the ones in the markup.
- UI has direct labels and live status badges (online/offline/waiting).

Potential barriers:
- Translation quality depends on source transcript quality and external translation availability.
- Scripture is the exception: a verse that was read is looked up in a real
  Bible in the reader's language rather than machine-translated, so it arrives
  in the wording that congregation knows.

### 3.2 Users with disabilities

Current support in templates/UI:
- `aria-label`, `role`, and `aria-live` are used in multiple controls and status areas.
- Keyboard shortcuts exist: `/` opens the search, `g` returns to the top, `?`
  lists the rest, `Esc` closes a dialog; admin `Ctrl/Cmd+R`, `Ctrl/Cmd+S`.
- Font size, theme toggle, and TTS controls help readability and auditory access.
- **View modes**: Accessibility raises every tap target to 44px and thickens
  the focus ring; Elderly steps the whole page up a size. Both are under the
  gear, in Settings → View.
- Help behind a form label opens in a popover on a click, not a hover, so it
  is reachable on a phone.
- The theme crossfades rather than inverting in one frame, and does not
  animate at all for anyone who has asked for less motion.

Gaps:
- No dedicated focus-management workflow for modal dialogs.
- Drag-and-drop reorder is feature-rich but not fully keyboard-equivalent.
- Screen-reader behavior is not validated by automated accessibility tests.

### 3.3 Native speakers

- Fast operator workflow: continuous recognition with auto-restart and interim streaming.
- Power features: bulk import/delete, reorder, correction broadcast, multi-format export.
- Viewer customization: display mode, source-text visibility, search, font size, theme, read-aloud voice/rate/volume.

### 3.4 Common workflows

1. **Admin live session**
   - Log in at `/login` (admin server)
   - Select source language and start recording
   - Speech results stream to viewers
   - Correct items as needed
   - Export transcript data

2. **Viewer follow-along**
   - Open user URL `/`
   - A wizard asks once for a reading language and whether to read aloud
   - Wait for connection (`ready` event + history load)
   - Optionally enable reading aloud, and press "Hear a sample" to set the
     voice, speed and volume before the sermon starts
   - Download local export from viewer UI

3. **Projection screen**
   - Open `/projection` on the machine driving the projector
   - It asks which room to follow, which language to show, and whether the
     room is dark; it remembers the answers and writes them into the address,
     so a second screen can be set up by copying the URL
   - `s`, or the gear beside the clock, reopens that wizard
   - Nothing else on the screen can be pressed: it is a display

Common errors and resolution:
- Microphone denied: browser permission and HTTPS/browser compatibility checks
- No live updates: verify user server availability and WebSocket connection state
- No read-aloud voice: the device has none for that language; install one in the system settings
- Missing translations: fallback behavior may show source text if translation fails

## 4. Administrator Perspective (Admin)

### Install with one command

On Linux (or a Mac, with Docker):

```bash
curl -fsSL https://github.com/gahingwoo/ezy_speech_translate/releases/latest/download/install.sh | sudo bash
```

It asks how to install, then downloads the latest release from GitHub,
checks it against the release's SHA-256 sums, and installs it:

| | Native | Docker |
|---|---|---|
| Runs as | two systemd services under an `ezyspeech` account | one container |
| Code | `/opt/ezyspeech/releases/<version>/`, each with its own Python environment | built as the image `ezyspeech:<version>` |
| Settings, secrets, transcripts | `/var/lib/ezyspeech` | the volume `ezyspeech_ezyspeech` |
| Needs | Linux with systemd | Docker (offered on Linux if missing) |

The installer asks about ports, HTTPS (browsers allow the console's
microphone only over HTTPS or on the machine itself), and the admin password,
which it makes for you unless you type one; nothing starts with a default.
If Cockpit is installed it offers the EzySpeech module. An install made by
the old `ezy_manager.py` is found, and its settings, password and transcripts
are brought over. `--yes` takes the defaults; `--help` lists the options.

Running it again on a machine that has EzySpeech opens a menu instead:
update, status, restart, a new admin password, the log, a backup, uninstall.

### Running it

Everything is the `ezyspeech` command, which the installer puts on the path:

```bash
sudo ezyspeech status            # what is installed and whether it is up
sudo ezyspeech check-update      # is there a newer release?
sudo ezyspeech update            # install it
sudo ezyspeech rollback          # back to the release before
sudo ezyspeech restart           # also start, stop
sudo ezyspeech logs -f
sudo ezyspeech password          # --generate makes one and shows it once
sudo ezyspeech backup            # settings, secrets and transcripts, as .tar.gz
sudo ezyspeech uninstall         # --purge deletes settings and transcripts too
```

An update keeps the running release and prepares the new one beside it,
switches over with a restart, and checks both servers come up reporting the
new version. If they do not within a minute, it switches back and says so.
The two most recent releases are kept, so `rollback` is a restart.

The Cockpit module does the same from a browser, through the same command,
for either kind of install. Its source is
[gahingwoo/ezy_speech_cockpit](https://github.com/gahingwoo/ezy_speech_cockpit);
each release carries a built copy.

### Releasing

The version is in `VERSION`. To release, change it, commit, and push a tag
`v<version>`. The release workflow checks the tag and `VERSION` agree, builds
the package, the Cockpit module and `SHA256SUMS` with `ops/make-release.sh`,
and publishes them with `install.sh`. Running that script by hand builds the
same files to test with.

### Other deployment paths

- `python3 setup.py` (local development setup: secrets, venv, optional SSL)
- `docker compose up -d --build` in a copy of the code (development)

### Configuration

Primary file: `config/config.yaml`
Key sections used by runtime:
- `server.*`, `admin_server.*`
- `authentication.*`
- `advanced.websocket.*`, `advanced.security.*`, `advanced.performance.*`
- `logging.*`
- `oem.*`
- `features.*`

Secrets flow:
- Signing secrets encrypted in `config/secrets.key`, loaded by `secure_loader.py`
- The admin password is kept only as a PBKDF2-SHA256 hash (600,000 rounds,
  salted) of the SHA-256 the login page sends, so nothing in the file can be
  used to sign in or turned back into the password. An older install's
  password is converted on the first start and the recoverable copy deleted
- There is no default password. To set or change it, then restart both
  servers: `sudo ezyspeech password` (or `--generate`) on an installed copy,
  which restarts them itself; `python -m app.auth.set_password` in a checkout

### Start/stop services

An installed copy (see "Install with one command"):
- `sudo ezyspeech start` / `stop` / `restart`
- `sudo ezyspeech status`
- `sudo ezyspeech logs -f`

Manual (development):
- `python app/user/server.py`
- `python app/admin/server.py`

### Logging and monitoring

- Main logs: `logs/app.log` (rotating handler)
- Security logs: `logs/security.log`
- Default app log rotation (from `config/config.yaml`): `max_bytes=10485760` (10MB), `backup_count=5`.
- Health endpoints:
  - user server: `GET /api/health`
  - admin server: `GET /health`
- Admin UI polls user health (`/api/health`) and shows client/translation counts.

### Debugging and troubleshooting

- Verify login/session path on admin server (`/api/login`).
- Verify admin-to-user connectivity (`/api/config` on admin gives user URL).
- Check browser console for Socket.IO reconnect/auth failures.

### Security considerations and permissions

Implemented controls:
- JWT validation for protected endpoints
- Session auth on admin panel
- Request size limits and sanitization
- Client/session-based blocking and rate-limit escalation
- CSP and security headers
- Optional HTTPS with cert files under `config/ssl`

Operational cautions:
- `config/secrets.key` is sensitive and machine-local.
- Debug endpoints exist in admin server (`/api/debug/*`) and must be removed or fully disabled in production deployments.

## 5. Developer Perspective (Developer)

### 5.1 Code Structure

- `app/user/server.py`: core backend + viewer APIs + websocket event hub
- `app/admin/server.py`: admin auth/frontend host + selected admin APIs
- `app/static/js/user.js`: viewer state machine, pagination, translation/TTS pipelines
- `app/static/js/admin.js`: operator workflow and microphone recognition handling
- `app/templates/*.html`: login, admin console, settings, listener, projection.
  **Generated.** Edit `tools/patternfly/render_*.py` and re-run it; a change
  made directly to a template is lost the next time anyone regenerates
- `app/i18n/strings.js`: every interface string in all 22 languages. Pages do
  not load it: `node tools/i18n/build.mjs` splits it into one file per language
  in `app/static/js/i18n/`, plus `core.js`, which loads English and the
  languages a page may be shown in, and fetches any other on demand. Run it
  after editing the strings, and commit what it writes
- `app/translation_service.py`: translation API wrapper
- `app/oem_manager.py`: brand config composition
- `secure_loader.py`: encrypted secret loading/migration
- `install.sh`, `ops/ezyspeech`: installer and the command that runs an install; `ops/make-release.sh` builds a release; `setup.py` sets up a development checkout

### 5.2 Core Logic

- Real-time channel is Socket.IO. History is an in-memory list, written through
  to SQLite when `database.enabled` is set, so a restart mid-service does not
  lose what has been said.
- Translation items are ID-based and broadcast to the listeners in one room.
- Viewer history loading uses tokenized paginated HTTP API (`/api/translations`).
- Viewer translation path:
  1) pushed by the server: each screen announces its reading language, and
     the server translates every line once per language in the room and sends
     it as `line_translated`; kept on the line for screens that load later
  2) server `/api/translate`, if nothing has arrived after six seconds
  3) client-side fallback logic if needed
- Viewer read-aloud path: the browser's own speech synthesis, nothing on the
  server
- A line already in the language being read is shown, not translated: no round
  trip and no waiting states.

**Scripture.** Two passes over every finished line, both local:

1. `bible_detector.py` reads references — "John 3:16", "第三章十六節" — and
   looks the passage up in the reader's own Bible.
2. `scripture_matcher.py` reads *wording*, because a sermon quotes far more
   often than it cites. Verses are indexed under their four rarest words
   (`app/data/bible/web_index.json`, built by `tools/bible/build_index.py`).
   A line looks up its own words, the candidates are ranked by how much of the
   verse's vocabulary appears, and the top 40 are measured by the longest run
   of words said *in the same order* as the verse. A paraphrase shares plenty
   of words with a verse but almost never eight of them consecutively.

   Eight words in a row plus 55% coverage and the verse replaces the line;
   five plus 30% and it is offered quietly underneath; below that the page
   says nothing. The rule the thresholds serve is that a wrong verse in a
   service is worse than no verse. Measured against the 37,565-verse index:
   99.7% exact on a verse read verbatim, 99.3% with a word in eleven dropped,
   91.3% when only half of it is read, and 97.3% silence on heavy paraphrase.
   On real sermon speech it substitutes a verse for about 1.3% of lines.
   Roughly 1 ms per line.

### 5.3 Key Design Decisions

- **Two-server split**: admin UI and user backend are separated by port/process.
  - Trade-off: cleaner role boundary, but more cross-service config complexity.
- **In-memory history, optionally written through to SQLite**: simple and fast
  to read, durable when it matters.
  - Trade-off: two places hold the same thing, and they can disagree if a
    write fails.
- **Browser speech recognition**: avoids server ASR dependencies.
  - Trade-off: browser compatibility and permission constraints.
- **Socket + paginated HTTP hybrid**: avoids sending full history over websocket.
  - Trade-off: token/session lifecycle coordination is required.
- **Generated templates**: the markup for five pages is built by Python, so a
  PatternFly component is written once and every page gets the same one.
  - Trade-off: nobody can fix a page by editing the HTML they are looking at.
- **One reading language**: the language a listener reads is the language the
  sermon is translated into *and* the language of the buttons and headings.
  - Trade-off: someone who wants an English interface over a Cantonese
    translation cannot have it. That is what "Keep the page in English" is for.
- **A vendored PatternFly subset**: `tools/patternfly/build.sh` assembles only
  the components the pages use.
  - Trade-off: using a new component means adding it to that list first.

### 5.4 Issues and Improvements

Observed weak points from current code:
- `app/static/js/user.js` is very large and still contains at least one
  redefined function (`speakText` is declared twice; the later one wins).
  - Recommended follow-up: continue moving shared concerns out, the way
    `theme.js`, `sidebar.js`, `wizard.js` and `typewriter.js` were.
- The admin console's masthead repeats two entries that are already in its
  sidebar, so the same action exists twice on one page.
- Service setup is a dialog opened from a navigation item; a nav item that
  opens a modal is not navigation.
- `app/admin/server.py` uses broad CORS and includes debug endpoints that should be gated or removed in hardened deployments.
  - Recommended follow-up: disable `/api/debug/*` by default and expose only behind an explicit development-only config flag.
- Admin and user auth models are mixed (session + JWT + API token), which increases complexity.
- Translation history is memory-only; restart loses state.
- Some UI behavior and language strings are inconsistent between templates and JS.

## 6. API / Interfaces

### HTTP APIs (selected)

User server (`app/user/server.py`):
- `POST /api/login` -> admin JWT (for user-server protected endpoints)
- `GET /api/config` -> runtime config (auth required)
- `GET /api/oem-config` -> OEM payload
- `GET /api/health` -> service health
- `GET /api/history` -> full history (auth required)
- `GET /api/translations?offset=&limit=&api_token=` -> paginated history
- `POST /api/translations/clear` -> clear history (auth required)
- `GET /api/export/<json|txt|csv|srt>` -> transcript export (auth required)
- `POST /api/translate` -> single translation
- `POST /api/translate/batch` -> batch translation
- `POST /api/translate/cache` -> clear translation cache (auth required)
- `GET /api/rooms` -> public list of rooms, used by the room picker and by the
  projection screen's setup
- `POST /api/bible/lookup` -> verses for a set of references, in the reader's
  Bible, with how each one was found (`reference`, `wording`, `cited`, `offer`)
- `GET /api/bible/languages` -> which Bibles exist for which language
- `GET|POST /api/bible/source-translation`
- `GET /api/features` -> which optional features this install has on
- `PATCH /api/translations/<id>/translated` -> cache one client's translation
  back on the server so the next listener does not repeat the call

Admin server (`app/admin/server.py`):
- `POST /api/login` -> admin session + JWT
- `POST /api/logout`
- `GET /api/config` -> user server URL info
- `GET /api/oem-config`
- `GET /health`

### Socket.IO events (user server)

Inbound:
- `admin_connect`
- `new_transcription`
- `correct_translation`
- `clear_history`
- `import_transcription`
- `delete_items`
- `reading_language` (`{lang}`, or `null` for none): the language a listener
  or projection screen reads, so the server can translate for it

Outbound:
- `ready` (contains `api_token`, and `server_translation: true`)
- `realtime_transcription`
- `new_translation`
- `transcription_confirmed`
- `translation_corrected`
- `history_cleared`
- `items_deleted`
- `line_translated` (`{id, lang, source, translated}`): a line translated once
  per language present in the room and sent to the screens reading it;
  `translated: null` means the server could not, and the screen asks itself

## 7. Usage Examples

### Minimal local run (development)

```bash
cd ezy_speech_translate
python3 setup.py
python3 app/user/server.py
python3 app/admin/server.py
```

Run the two server commands in separate terminals (or run one in background) so both services stay available.

Open:
- Viewer: `http(s)://localhost:1915/`
- Admin login: `http(s)://localhost:1916/login`

### Translation API request

```bash
curl -X POST http://localhost:1915/api/translate \
  -H 'Content-Type: application/json' \
  -d '{"text":"Hello world","target_lang":"zh"}'
```

### Service operations (Linux/systemd path)

```bash
sudo ezyspeech start
sudo ezyspeech status
sudo ezyspeech logs -f
```

## 8. Appendix

### Dependencies

Runtime dependencies are declared in `requirements.txt`.
Primary production dependencies include Flask, Flask-SocketIO, eventlet, Flask-Limiter, Flask-Talisman, PyJWT, PyYAML, requests, and gunicorn.

### Build / setup process

Nothing is compiled to run the app; everything below is committed, so a fresh
checkout starts with no build step. The generators exist so that a change is
made once instead of five times.

- `setup.py` for local bootstrap and secret generation
- `install.sh` and `ezyspeech` for install, update, rollback and uninstall

Regenerating the front end, after editing a generator:

```sh
python3 tools/patternfly/render_user.py        # app/templates/user.html
python3 tools/patternfly/render_admin.py       # app/templates/admin.html
python3 tools/patternfly/render_config.py      # app/templates/config.html
python3 tools/patternfly/render_projection.py  # app/templates/projection.html
```

Rebuilding the vendored assets, which is only needed when a new PatternFly
component or icon is used:

```sh
sh tools/patternfly/build.sh          # app/static/patternfly/patternfly.css
python3 tools/patternfly/extract_icons.py   # tools/patternfly/icons.json
```

A component whose classes are used but whose name is not in the `COMPONENTS`
list in `build.sh` will simply have no styles. The same goes for an icon that
is not in the `NAMES` list in `extract_icons.py`, except that one fails loudly.

Rebuilding the scripture wording index, only needed if the source Bible
changes — the output is committed:

```sh
python3 tools/bible/build_index.py    # app/data/bible/web_index.json
```

### Version notes

The version is written in one place, `VERSION` at the root. The servers put
it in every page and in `/api/health`; releases, the Docker image and the
`ezyspeech` command all take it from there. To release, change `VERSION`,
commit, and push a tag `v<version>`: the release workflow checks the two
agree, then builds and publishes the release.
