# PatternFly 6 migration — handoff

Status as of 2026-09-06. Read this before touching the templates.

## What this migration was

The app was never on PatternFly. It borrowed the class names over ~75KB of
hand-written CSS — and borrowed them wrong: `pf-c-button--primary` is BEM, not
PatternFly's modifier syntax (`pf-m-primary`), and `admin.html` mixed PF4
(`pf-c-`) and PF5 (`pf-v5-c-`) names in the same file. No PatternFly stylesheet
was ever loaded. It is the real thing now, on all four pages.

## Rules the owner set

- **Front end first.** Backend work was allowed for the config page and for
  nothing else.
- **Never touch `config/secrets.key` or the config storage format.** Installs in
  the field decrypt `admin_password`, `jwt_secret` and `server_secret_key` from
  it. Change the format and an upgrade locks the admin out, invalidates every
  issued JWT and drops every session. Upgrades must be seamless.
- **`captions.html` is out of scope.** It is a transparent overlay for OBS
  (`--cap-bg: transparent`, two divs, 27KB of inline JS). PatternFly has no
  component that fits it, and loading 1MB of CSS there risks overriding the
  transparent background that makes the overlay work.
- **Rewrite means fork.** Back up the original, then write from a blank file.
- **No emoji.** Not in the templates, not in the JavaScript, not in the
  translated strings.

## Done

**`login.html`** — PatternFly's Login component. `login.css` 3.4KB → 1.8KB. The
sign-in error is a helper text in its error state.

**`user.html`** — generated by `render_user.py`. `user.css` 42KB → 15KB.

**`admin.html`** — generated by `render_admin.py`, written from a blank file.
`admin.css` 30KB → 17KB, also from nothing. The sidebar's four secondary panels
are expandable field groups.

**`config.html`** — generated by `render_config.py` from `config_schema.py`.
The settings page, 59 fields, replacing the YAML textarea.

**Icons** — `extract_icons.py` pulls them out of `@patternfly/react-icons` into
`icons.json` (56 of them). The generators inline them. Markup the JavaScript
builds as strings uses `svgIcon(name)`, which points at a `<symbol>` sprite the
generators emit into the page.

**Static file versioning** — `app/core/static_version.py`, one content-hash
helper registered on both servers, used by every template.

## Tools

    sh     tools/patternfly/build.sh              # vendor the CSS bundle
    python3 tools/patternfly/extract_icons.py     # refresh icons.json
    python3 tools/patternfly/render_user.py
    python3 tools/patternfly/render_admin.py
    python3 tools/patternfly/render_config.py
    python3 tools/patternfly/check_contract.py A.html B.html

`build.sh` takes a component list — **check a component is in it before using
that component's classes.** Backups of the originals are in `backup/`.

## check_contract.py, and what it does not catch

It diffs every `id`, inline `on*` handler, `data-i18n` key and Jinja block
between two versions of a template. Run it after every regeneration.

**An element's id is an API the JavaScript calls. Never rename one.** The first
run against the `user.html` rewrite found 16 missing ids, 6 missing handlers and
16 missing translation keys, all from renaming things while porting them
(`rateSlider` → `speedSlider`). The page rendered perfectly and the sliders were
dead.

It does **not** read inline `<script>` blocks. The `user.html` rewrite dropped
the page's room-picker script and nothing noticed: the room picker and the
sidebar's room switcher simply never appeared. If a template has a script in it,
diff that by eye.

Current state: `admin.html` 71/73 ids (the two that left are the config editor,
which moved to `config.html`), `user.html` 67/67.

## Traps found the hard way

**PatternFly separates surfaces by ground, not by lines.** The page is the
secondary grey, the main container is a white sheet floating on it with a radius
and a shadow, the sidebar is transparent over the grey. Drawing dividers between
them and painting the container grey is what made both pages look flat and made
the white stop where the content stopped. Do not add those rules back.
`--pf-v6-c-page__main-container--AlignSelf` is `start`, so the sheet ends with
its content; both stylesheets set it to `stretch`.

**Do not write into an element PatternFly or i18n.js owns.** Four separate bugs
were this:
  - `i18n.js` wrote to `span:last-child` of the status badge, which is the
    label's content wrapper, so every language pass flattened the label
  - the tour's step icon was nested inside a `data-i18n` element, whose
    `textContent` is replaced wholesale, so the first language pass deleted it
  - `user.js` replaced the TTS button's icon SVG with an emoji, permanently
  - `admin.js` replaced the record button's whole class list, so PatternFly's
    modifiers had to be what it writes

**A class the JavaScript sets is the contract, not the `hidden` attribute.**
Every dialog on the listener page carried `hidden` from the rewrite while
`user.js` opens them with `.active`; the attribute won and none of them ever
opened. Same for the mobile search bar, the scroll-to-top button, the
announcement banner and the Bible hint. Check what the JavaScript actually does
before choosing how the stylesheet hides something.

**A computed style can contradict the stylesheet — look for inline styles.**
Section headings were buried because `user.js` set `style.display = 'block'`,
and an inline style beats a stylesheet. Setting `''` hands the element back.

**Check the component is in the bundle.** `pf-v6-c-toolbar` had no styles
because Toolbar was not in `build.sh`'s list; it collapsed to `display: block`
and stacked the masthead vertically. Table, DescriptionList, Check, Panel,
Spinner and DragDrop were all missing too. Also: `pf-v6-c-toolbar__content` does
not exist (only `__content-section`), `pf-m-grey` is not a PatternFly 6 label
colour, `pf-mono` is not a PatternFly class, and neither
`--pf-t--global--background--color--brand--default` nor
`--pf-t--global--background--color--status--danger--default` is a token. Grep
the vendored CSS; a rule using a token that does not exist silently does
nothing.

**`z-index: -1` sits below a painted body.** On the login page the background
pattern was invisible because the page colour was on `body`. Put it on `html`.

**The sidebar drawer is PatternFly's, not ours.** Below xl it already slides the
sidebar out and back with `.pf-m-expanded`; both pages map `.mobile-open` onto
the same two tokens rather than positioning it by hand. The open drawer needs
lifting over its own backdrop — the sidebar is at z-index `sm`, the backdrop at
`lg`.

**OEM hooks are load-bearing.** `oem-loader.js` queries `.brand span:first-child`,
`.brand span:last-child`, `.login-logo h1` and `.login-logo-icon`. Those class
names and the order of those spans must survive any rewrite. It also decides
which page it is on: it used to read the path, and the admin panel is served at
`/`, so it relabelled the admin brand with the listener's title. Pages name
themselves with `<body data-page="...">` now.

## The settings page

`GET`/`POST /api/config/fields` on the user server, proxied by the admin server.
The body is `{"changes": {"server.port": 1915}}` — dotted paths to single
values. A path that is not already in the file is refused, so is one that does
not hold a scalar, and so is any path ending in a key from
`_SENSITIVE_CONFIG_KEYS`. Values are fitted to the type already in the file.

Writes edit the changed lines in place, so the comments and the layout survive;
it falls back to dumping the document if a line cannot be safely rewritten, and
the result must parse back to what was intended before anything is written.

The old `POST /api/config/raw` is still there, behind a fold on that page, for
anything the fields do not model. It still rewrites the whole file and drops the
comments, and the page says so.

To add a field: put it in `config_schema.py` and re-run `render_config.py`. The
path has to exist in `config/config.yaml` already.

## Verifying

Only one server can hold port 5000. Kill both before starting one, or you will
test the wrong page.

    pkill -f run_user.py; pkill -f run_admin.py
    lsof -ti:5000 | xargs kill -9
    venv/bin/python run_admin.py     # or run_user.py

The admin dashboard and the settings page both redirect to `/login` without a
token, so they cannot be opened without the admin password. To look at one,
render it to `app/static/_preview_*.html` with `render_template` and open that;
put a token in `localStorage` if the page's own JavaScript needs one. **Delete
the preview files afterwards.**

Before testing anything that writes: `cp config/config.yaml` somewhere, and diff
it back when you are done.
